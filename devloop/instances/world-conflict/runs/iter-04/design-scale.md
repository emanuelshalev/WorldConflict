# Design: one layout that scales with the resolution (D-87)

UX Designer, 2026-11-24. Implements D-87: the reference screen is 1920x1080; a larger screen of the same shape (2560x1440, 3840x2160) shows the 1080p layout scaled up. Other shapes are the later screen-size pass and must not get worse. Claims below were read in the code at `e4202cd`; anything not verified is marked **(assumed)**.

## 1. Findings

**Game screen.** Six width classes and four height flags, defined twice with the same numbers: `ui/src/lib/layout.ts:13` (`BP`, `layoutFor` at :33, read from `window.innerWidth/innerHeight` at :51) and the media queries of `ui/src/styles/layout.css` (header :10-17). JS picks the region forms (`Desk.tsx:121-132` list column, Plan rail or bar; `MapMonth.tsx:49-80` Plan float, Map List; `AgendaList.tsx:74,155`; `MonthBar.tsx:32-46`; `YourMove.tsx:156,649`, where the number of rows grows with height, up to 10 at 2000 tall). CSS changes column widths per class (`layout.css:58-75`, `:405-415`, `:475-481`), the state band goes to one line at 3200 (`state-band.css:42`), and tall flags add content (`layout.css:184-206`: fill rule at 900, detail lines at 1200, "What your advisers say" at 1300). The Thing lays itself out by its own width with container queries at 38, 56 and 96rem (`layout.css:151-170`). Fit rules compare `scrollHeight` with `clientHeight` (`layout.ts:107,123`), layout pixels, not screen pixels.

**Type.** `html { font-size: clamp(16px, calc(0.42vmin + 11.5px), 22px) }` (`layout.css:21`): 16.04 px at 1080 tall, 17.55 at 1440, 20.57 at 2160 (phones fixed 16 px, :419). So the type grows 9% and 28% where the screen grows 33% and 100%.

**Units.** Counted in the CSS files under `ui/src` (literals): about 4,790 `px` against 434 `rem`, so about 92% px. The rem is almost all in `layout.css` (343 rem, 135 px), `state-band.css` (40 rem) and `result.css` (29 rem). Everything else is px: `wc.css` 770, `title.css` 553, `reveal.css` 524, `month.css` 455, `App.css` 448, `orders.css` 422, `learn.css` 350. Plus 155 inline `style={{...}}` objects with numbers in TSX, and px constants in JS placement code (`CountryPicker.tsx:115` 300-380 px, `OrderCard.tsx:547-549` 260 px). About 120 `vw`/`vh` uses (layout 26, title 21, wc 18, result 9); `cqw` only in `wc.css:1835,1850` and `scenes.css`.

**Other screens.** Each has its own breakpoints, none tied to `BP`: title at 900 and 1279 (`title.css:84-397`, `TitleScreen.tsx:219`, `globeFit.ts:20` PHONE_MAX 900) with `clamp(34px, 4vw, 52px)` headings; result card and paper at 1280, 1600-2239 and 2240 (`result.css:129-169`; the paper's columns are `22rem`, so 4 at 1920 and 6 at 3440); world map and HUD at 520-1439 (`wc.css:238-2089`), all px; reveal at 700 and 1180 (`reveal.css:1566,1614,1920`), a fixed 220 px rail (`reveal.css:11`). Three components portal to `document.body` (`Explainer.tsx:381`, `CountryPicker.tsx:293`, `OrderCard.tsx:574`) and place themselves from `getBoundingClientRect` and `innerWidth`.

## 2. Options

**(a) Scale the root font size, everything in rem, classes on the design size in JS.** Root = 16 px x s. Works only for what is in rem: today the desk regions partly (order cards, month screen, HUD, title, reveal, paper body are px). Breaks: media queries cannot follow (em in a media query is the initial 16 px), so every rule with a threshold between 1920 and the real width must become a JS attribute; JS px constants and inline styles need x s; MapLibre labels and icons stay native size (the map would show more world, not a bigger map) unless the zoom level is offset by log2(s). Text stays sharp. Covers: whatever is converted. Work: about 4,800 px literals and 155 inline styles to convert and re-check on every screen; 2 to 3 engineer weeks; high regression risk below 1920.

**(b) CSS `zoom` on the document root, classes from innerWidth/s and innerHeight/s.** Support: Chromium shipped the standardized `zoom` in 128 (Aug 2024), Firefox in 126 (May 2024), Safari has a long-standing non-standard implementation **(assumed: Safari's rect and event coordinates under zoom need the spike)**. Playwright 1.56 runs a recent Chromium. Effects: layout happens at the design size, so fit rules (`scrollHeight`/`clientHeight`, ResizeObserver sizes) see 1920x1080 and behave as at the reference. `position: fixed` stays relative to the viewport (zoom makes no containing block), so the reveal and overlays still cover the screen. Media queries still see the real viewport: rules with a threshold above 1920 wide or 1080 tall must move to attributes (a short list, see WP-2). `getBoundingClientRect` returns screen (zoomed) coordinates, consistent with `clientX`, but a `left`/`top` written back in px is multiplied by s, so placement code must divide by s **(assumed per the standardized model; spike checks)**. `vh`/`vw` resolve against the real viewport and are then zoomed **(assumed)**, so `100vh` would overflow: the root size and the game's vh/vw must use design units. MapLibre sizes its canvas from `clientWidth x devicePixelRatio` (layout px), so the map is drawn at 1920 and upscaled (soft) unless `pixelRatio = devicePixelRatio x s`; its pointer math divides by `rect.width / offsetWidth` **(assumed from MapLibre's DOM scale correction; spike checks)**. Playwright guards keep working in screen px. Covers: every screen, portals included (they live under the root). Work: 4 to 6 days.

**(c) `transform: scale(s)` on a fixed 1920x1080 stage.** Exact for 16:9 only; other shapes letterbox or need a second path, which makes laptops and ultrawides worse. Fixed elements inside become relative to the stage; body portals must move into it. Rects are transformed while `innerWidth` is not, so placement code breaks as in (b). Text and the map are rasterized then scaled: soft at 1.33, and composited layers (animations) can blur. Covers every screen inside the stage. Work: 3 to 5 days, but fails "not worse" for other shapes.

**(d) Keep the classes, make D the only arrangement for 16:9 at 1920 and up.** Same arrangement, not scaled: at 3840x2160 the regions grow by the root (1.28x) and the Thing by the rest, text stays small. Does not meet D-87. Title, reveal, result card and paper unchanged. Work: 1 to 2 days.

## 3. Recommendation: (b), CSS zoom with a design size

**Rule.** `s = clamp(1, min(innerWidth / 1920, innerHeight / 1080), 3)`. Design size `dW = innerWidth / s`, `dH = innerHeight / s`. `document.documentElement.style.zoom = s`; `--dw`, `--dh`, `--dvmin` (design px) set on the root; `layoutFor(dW, dH)` everywhere instead of the window size.
- Lower bound 1: below 1920 wide or 1080 tall nothing changes (s = 1, design size = window). 1366x768 to 1919 wide keep today's T, L and D arrangements and fit rules exactly. No downscaling in this pass.
- 16:9 at 1080 and up: dW x dH = 1920x1080, class D, tall; 2560x1440 is the 1080p screen x 1.333, 3840x2160 x 2.
- Upper bound 3 (5760x3240): beyond it the 1080p layout grows no further and the extra room is margin around the game **(choice; 8K at 100% is rare)**.
- While s > 1 the class is capped at D. W and U stay in the code, reachable only at s = 1 (for example 2560x1080 or 3440x1080), so those shapes keep today's behaviour until the screen-size pass.
- Ultrawide 3440x1440: s = 1.333, design 2580x1080, class D. I correct the proposal: the side regions keep their D widths (List 20rem, Plan 25rem); the Thing takes the extra width and, at 116rem, shows its third column by the existing container rule (situation | answers | context map). That arrangement already exists and passed review at 3440 (L-2: width goes to Thing columns). Map mode: card `clamp(26rem, 26vw, 42rem)` on the design width, map between, Plan float.
- Tall shapes keep their flags on the design height: 1920x1200 unchanged; 2560x1600 is 1920x1200 x 1.333 (detail lines shown).

**Root font.** `html { font-size: clamp(16px, calc(0.42 * var(--dvmin) + 11.5px), 22px) }`: same formula on the design size, so it is 16.04 px for every 16:9 at 1080 and up (zoom does the rest), and 1920x1200 or 1600x1200 keep today's size. Phones stay 16 px.

**What moves.** At 2560x1440 and 3840x2160 the player gets the 1080p content: the advisers' voices, the detail lines and the Map List under the card are no longer shown in place; they stay one control away (Ask your staff, which is shown again; See all in Map mode). No capability is removed. At 3440x1440 the Thing keeps its third column but loses the voices block and the List under the map card the same way.

**Sharpness.** Zoom lays text out at the final size (as browser zoom does), so type and SVG (scenes, outcome maps) stay sharp; 1 px borders round to whole device pixels. Raster art is shown at s times its CSS size, as at 3440 today. The maps get `pixelRatio = devicePixelRatio x s` (`MapView.tsx`, `TitleGlobe.tsx`), so their backing store matches the screen (3840x2160 at s 2, as native 4K today); label sizes then scale with everything else.

## 4. Acceptance checks (automated, no reviewer)

New guard `scenarios-qa/regressions/DR-SC-1.mjs`, Hormuz Convoy as the United States, seed 4242, desk month 1, desk month 4, Map month 4, result card, paper, title, reveal stage 0, at 1920x1080, 2560x1440 and 3840x2160:
1. `documentElement.currentCSSZoom` is 1, 1.333, 2 (within 0.001) and `layout.cls` is D at all three.
2. Every `[data-region]`, `[data-form]`, `.opt`, `.lrow`, `.prow`, Execute and the state band: box at size X equals its 1920 box x s, within 1 px per 100 px on each edge.
3. Same text per heading and button, same number of lines per heading (`height / line-height` rounded), allowing one line of difference only where the 1920 line is within 2% of its box width (subpixel metrics differ between zoom levels).
4. Same counts: List rows, Plan rows, answer cards, catalogue tiles, paper columns and stories, folded sections; same `data-fit` level on every fitted element.
5. No inner or page scroll, nothing under 15 px rendered (computed size x zoom), map canvas `width` = screen px x devicePixelRatio.
6. Below the reference nothing moves: the existing 1024, 1366x768, 1440, 1920x1080 and 390 baselines pass unchanged, with no `--update-visual`.
7. A click on a map country at 2560x1440 opens the same country as at 1920x1080 (pointer mapping), and an order's hover forecast and the country picker open beside their trigger, inside the screen.

Adapt, not weaken: `RS-008-1.mjs` AC-L14 (expect 16.04 at every 16:9 from 1080 and check the zoom), AC-L13 forms and AC-L10/AC-L3 on the design size (`W/s`, `H/s`); `RS-008.mjs` keeps its sizes, its expected forms follow the design size; `DR-MS-4.mjs` reads the voices block at 3440x1440, which no longer shows there: run it at 1920x1440 (design height 1440, block shown) or read the same voices through Ask your staff, same rule; `DR-MS-1/2` and `RS-008-2` keep 3440x1440 with the new layout. Baselines: the five 3440x1440 ones (`layout-desk-m1`, `layout-desk-m4`, `layout-map-m4`, `layout-result`, `layout-paper`) are retaken once (intended change, reviewed against 1920). No 2560 or 3840 baselines are added: check 2 makes them redundant; optionally the 3840 screenshot downscaled by 2 is compared with the 1920 baseline.

**Risks.** (1) Main risk: browser zoom is young as a standard; Safari's older model and MapLibre's pointer and canvas handling under zoom are not yet verified (WP-0 first, fall back to scaling the map container's pixel ratio and an explicit pointer transform if needed). (2) Text metrics differ slightly between zoom levels, so line-break equality needs the tolerance in check 3 or it flakes. (3) Content that only tall screens showed (voices, detail lines, Map List) now sits behind one control on large 16:9 screens; the owner may want it back in the screen-size pass. (4) GPU memory: the maps' backing store at 5K with devicePixelRatio 2 and s 1.33. (5) Any later px written from a rect without dividing by s is a silent bug at s > 1 only; check 7 and a lint note in `layout.ts` cover it.
